Choose the source data

Three NM2 words used below: A case is one observation that NM2 analyses—for example one person, participant, scan or sample. A modality is one block of measurements collected for a set of cases, for example questionnaire scores, MRI voxels, ROI values or connectivity edges. A feature is one input measurement that the machine-learning model uses.

Use this source when each case is represented by measurements from named brain regions (ROIs) rather than individual voxels or surface vertices.

  1. Choose the ROI input format: CAT12 ROI files, a workspace matrix/table, or a table file.
  2. Select or add the ROI measurements and identify the cases.
  3. For matrix/table ROI input, provide the ROI identity information so NM2 knows which data column belongs to which region.
  4. Select the required spatial reference: a labelled volumetric atlas or a surface annotation, depending on the ROI type.
  5. Provide labels and optional covariates. Use Case-ID mapping when the separate metadata contain Case IDs.
  6. Run Preview and verify the number and order of ROIs and the spatial QC before Commit.
Your responsibility: make sure that the ROI names/IDs and their order match the columns of the ROI data, and that the selected atlas or surface annotation describes those ROIs. NM2 does not infer region identity from column position alone.
Advanced details

ROI import retains the explicit ROI identity and spatial reference so that imported columns can be linked to atlas/annotation regions in QC and downstream viewers.

Case alignment

For image, surface, connectivity and ROI imports, the main source data define the cases. When labels or covariates are stored separately in MATLAB variables or tables, NM2 must match those rows to the source cases.

  1. Use Case-ID mapping when the label/covariate data contain a Case-ID variable.
  2. Select the Case-ID variable that identifies the rows of the label or covariate data.
  3. Use Explicit row order only when the metadata have exactly the same number of rows as the source cases and row 1, row 2, and so on refer to the same cases in the same order.
  4. Run Preview and check the final case count and the label/covariate summary.
Your responsibility: if you choose Explicit row order, you must verify the row correspondence yourself because NM2 does not match the rows by identifier.
Advanced details

Case-ID mapping uses the common DataIO case matcher. Explicit row order bypasses identifier matching and uses the source order exactly as supplied.

Shared key

Shared key is not used for this source type. Use the Case-ID controls or alignment options shown for this source instead.

Advanced details

Shared key is the tabular mode for data in which the same Case-ID column(s) exist in every selected table. This source establishes case identity through its own Case-ID controls before the data enter the common DataIO matching path.

Key per block

The generic Key per block panel is not used for this source type. When labels or covariates come from separate data with their own Case IDs, select the appropriate Case-ID variable beside those label/covariate controls.

Advanced details

The label or covariate rows are matched to the source case list through the Case-ID variable assigned to that metadata block.

Explicit row order

Explicit row order assumes that the separate label/covariate data have exactly the same number of rows as the source cases and that the order is identical. For example, metadata row 1 must belong to source case 1, metadata row 2 to source case 2, and so on.

  1. Choose Explicit row order only after you have verified the order and row count.
  2. Run Preview.
  3. Check the final case count and the label/covariate distribution before Commit.
Your responsibility: make sure that these assumptions are met by the data. If you cannot verify the order, use Case-ID mapping instead.
Advanced details

NM2 does not match metadata rows by identifier in this mode. It assigns them to source cases by row position.

Row filters

The Advanced tabular row filters panel is not used for this source type.

If cases must be excluded, select the required files/cases in the source-specific controls or prepare the source data before import. Then run Preview and check the final case list/count.

Advanced details

Tabular row filters operate on tables and worksheets. Image, connectivity, surface and other non-tabular sources use their own case/file selection and then enter the common downstream DataIO alignment and validation path.

Labels

Labels are the values that you want the model to predict. When classification labels are generated from class-specific file blocks, the label controls are hidden because those file blocks already define the labels.

  • For classification with explicit labels, select the label variable or column. NM2 derives the classification group names from the distinct label values; there is no separate group-name editor.
  • For regression, select the numerical target variable(s) or columns. For CSV/spreadsheet input, target names are taken from the selected column headers.
Required file format: Every TXT, CSV or TSV file used for labels, covariates or user-supplied global values must have a header row containing column names, even when the file has only one column. The first row is interpreted as column names, not as data. Put the first case value on row 2. For example, a single-column label file starts with Diagnosis on row 1, followed by one label per case. Headerless files are not supported; add a header before importing.
  1. Select the label variable or column(s) when explicit labels are required for this import.
  2. If the labels are matched by Case ID, select the Case-ID variable or column(s) that identify their rows.
  3. Use Explicit row order only when the label rows have exactly the same case order as the modality.
  4. Run Preview and check the class counts or target summary.

Leave genuinely missing labels missing. Do not replace them with an invented class or numerical value.

For workspace covariate-matrix naming (variable selection or comma-separated name file), see Covariates.

Your responsibility: verify that the selected label values or regression targets have the intended scientific meaning for the aligned cases.
Advanced details

Labels use the same DataIO source, Case-ID/composite-key, row-order and role-assignment machinery as tabular data. Training classification data define the raw source value → canonical NM2 class mapping once; labelled OOCV data reuse that mapping. Missing labels remain NaN, and an OOCV class value absent from training is a blocking error.

Covariates

Covariates are optional case-level variables that NM2 stores separately from the main features, for example age, sex, site or scanner. For CSV/spreadsheet input, covariate names are taken directly from the selected column headers.

  1. Select the covariate variable(s) or columns if your analysis needs them.
  2. For MATLAB-workspace covariates, select a Covariate-name variable (a cell array or string array with one name per covariate column), or use Load names from file to read a comma- or line-separated list from a TXT, CSV or TSV file. You can also type the names manually. The number and order of names must match the covariate-matrix columns.
  3. If covariates are matched by Case ID, select the Case-ID variable or column(s) that identify their rows.
  4. Choose whether the new covariates are added to the existing covariates or replace them.

Leave the covariate assignment empty when the analysis does not use covariates. Where the imaging provenance supports a global value, configure it independently; its source and alignment do not have to be the same as the label/covariate source.

Advanced details

Covariates use the generic DataIO role and alignment machinery and are committed as a separate case-level matrix. Supported global values use the same generic source/alignment machinery but remain an independent source because imaging software commonly stores global measurements separately. Missing covariate values are retained and reported; downstream preprocessing or analysis determines how they are handled.

Preview

  1. Complete the controls marked as required, then click Preview.
  2. Check the number of cases and features that NM2 plans to import.
  3. Check the preview table and the class/target summary when labels are present.
  4. Open diagnostics and QC when NM2 reports a warning or blocker.
  5. If anything is wrong, correct the setup and run Preview again.
Preview does not change the committed NM dataset. It shows the data that NM2 will import if you press Commit with the current settings.
Advanced details

Preview materialises the current import setup and retains that result. Commit reuses the retained materialisation while the relevant import settings remain unchanged, which avoids unnecessary rereading of the source.

QC and diagnostics

Use QC and diagnostics to check the data before Commit.

  • Blocking: the stated problem must be corrected before Commit.
  • Warning: the warning itself does not block Commit, but read it and decide whether the data are scientifically acceptable.
  • Information: NM2 is reporting what it found or what it did.
  1. Read the first blocking message, if one is present.
  2. Identify the named file, table, variable, case or setting.
  3. Correct that item in the import setup.
  4. Run Preview again and re-check QC.
Your responsibility: a technically valid import is not automatically scientifically correct. Check that the cases, variables and labels are the data you intended to import.
Advanced details

Diagnostics are produced by backend source discovery, materialisation, validation and QC. The QC viewer uses the retained Preview materialisation rather than independently rereading the source.

Commit

Commit writes the Previewed data into the selected NM2 training modality or OOCV dataset.

  1. Run Preview and resolve every blocking diagnostic.
  2. Check the case count, feature count, labels and QC information.
  3. Click Commit only when these values describe the dataset you intend to create.
  4. Return to the modality overview and verify that the modality is listed and ready.
Your responsibility: Commit confirms that the current import setup is scientifically the one you want to store in NM2.
Advanced details

Commit transfers the validated retained materialisation into NM2 and stores the restorable scientific input settings and source description. If the retained Preview is no longer valid, the same DataIO materialiser runs again before Commit.

Modify / Resume

Use Modify to reopen the setup of a modality that has already been committed. Use Resume to continue an import task that was saved before Commit.

  1. Open Modify or Resume.
  2. Check the restored source, the feature/label/covariate/Case-ID assignments, the alignment settings and the filters.
  3. Re-enter live information that NM2 intentionally does not save, such as a database password.
  4. For database imports, rediscover the database/schema/table list before continuing.
  5. Run Preview again before recommitting.

Do not assume that a value shown after Resume proves that the external source is currently connected. Follow the red/green navigation borders and refresh live resources when requested.

Advanced details

Persisted scientific settings are rehydrated from DataIO state. Security-sensitive credentials and live external namespace catalogues are not persisted.

OOCV / application data

OOCV (out-of-cross-validation) data are independent cases to which an already trained model is applied, for example an external validation cohort or new clinical cases.

  1. Create or select the OOCV/application dataset.
  2. State whether true labels are available for these cases.
  3. Import the modality or modalities required by the trained analysis.
  4. Use the same scientific meaning and feature definition as in training.
  5. Preview and Commit each OOCV modality.

The OOCV dataset does not need the same number of cases or the same class proportions as the training dataset. If labels are present, their class values must correspond to classes that existed in training.

Your responsibility: make sure that each OOCV feature has the same meaning, units and preprocessing interpretation as the corresponding training feature.
Advanced details

Training defines the classification class mapping. Labelled OOCV data reuse that mapping. DataIO can store an OOCV dataset while only some modalities are present; the selected trained analysis determines which modalities are required before application can run.

Public API

If you are importing data through the graphical DataIO interface, you can ignore this section. The public API is for reproducible MATLAB scripts that perform the same imports without clicking through the interface.

Advanced details

The browser and public API converge on the same DataIO authorities. Example:

spec = struct('sourceType','roi','sourceFormat','workspace_matrix', ...
    'modeflag','classification','description','Regional volumes');
[NM,out] = NMDataIOAPITools.importTrainingROI(NM,spec);

Use the exact fields supported by NMDataIOAPITools for production scripts.
